# 一键交接：管理员生成密钥交接链接，收件人自助领取

**Status:** ✅ ACCEPTED · **Date:** 2026-10-11 · **Deciders:** 用户（"我直接用管理员账号去申请一个密钥，
然后把带密钥的链接……直接发给他。他拿到链接后直接就能去弄报告，不需要我再去平台上操作确认"）
· **Supersedes:** none · **Related:** `2026-10-10-agent-self-service-keys.md`

## 背景

现有自助申请流程是**两段式**：agent `POST /api/agent-keys/applications` 拿到 claim secret
→ 人类登录面板 → 在「待批准申请」里点批准 → agent 轮询领取。

用户诉求：**去掉中间那次面板操作**。他要的动作是「我（管理员）生成一个东西，发给他，
他直接用」，全程不需要他再登录面板。

注意这**不是**取消「人类裁决」——裁决仍然存在，只是**提前到生成链接的那一刻**由管理员
一次性做出。安全性因此不降级：仍然没有任何明文密钥在服务端落盘。

## 关键设计：交接链接里放的是**一次性领取凭证**，不是密钥本身

| | A. 链接里直接带密钥 | **B. 链接里带一次性 claim secret（选定）** |
| --- | --- | --- |
| 实现 | 复用 `CreateManualKey`，把明文 token 放进 URL fragment | 建一条**已批准**的 application，fragment 里放 claim secret |
| 收件人动作 | 打开即见密钥 | 打开 → 点「领取密钥」→ 见密钥 |
| 链接泄漏的后果 | **永久可用**的密钥（聊天记录、群、转发都会泄漏） | 只能领一次、到期自动失效；密钥本身从不在链接里 |
| 与既有不变量的关系 | 明文密钥会随着链接长期流转 | 完全沿用「密钥永不入库 / 明文只在领取那一刻存在」 |
| 成本 | 略少 | 多一个按钮与一个端点 |

选 **B**：用户会把链接发到聊天工具里，而聊天工具的链接预览、群成员、转发都会让链接
离开预期受众。一次性 + 有到期时间的凭证把这种事故的后果从「密钥泄漏」降为「有人抢先领了，
管理员撤销重发一条」。而多花的成本只是一个按钮。

## 裁决

| # | 问题 | 裁决 | 依据 |
| --- | --- | --- | --- |
| D1 | 管理员接口 | 新增 `POST /api/admin/key-handoffs`（**Session 鉴权**，与其它 `/api/admin/*` 一致） | 密钥管理面一律 Session 门禁，agent 凭据接触不到 |
| D2 | 落库形态 | 直接建一条 **status='approved'** 的 application（`CreateHandoffApplication`，单事务），不建 pending 再批准 | 避免「批准失败留下一条待批垃圾」，也让管理员无需再看队列 |
| D3 | 待批上限 | **不适用**于交接（不走 `KEY_MAX_PENDING`） | 那是防公开入口被灌爆的闸；管理员自己发起的不该被它挡住 |
| D4 | secret 的传递位置 | 放在 URL **fragment**（`/k/{id}#{secret}`），不放 path/query | fragment 浏览器不会发给服务器：不进访问日志、不进 Referer（本站还额外发 `Referrer-Policy: no-referrer`） |
| D5 | 链接有效期 | 复用 `KEY_APPLICATION_TTL`（默认 24h）作为 `claim_deadline` | 不再加新配置项；一天足够转发，过期就让管理员重发一条 |
| D6 | 密钥有效期 | 生成时由管理员选定（缺省 **24h**，显式 `0` = 永不过期），与既有批准端点同语义 | 「永不过期只能由人类显式给出」是既有约定 |
| D7 | 领取方式 | 页面按钮触发，**不自动领取** | 自动领取会被聊天工具的链接预览（会抓取页面）烧掉一次性凭证；预览器不执行 JS，而 claim 必须在客户端带 fragment 才能发起 |
| D8 | 页面地址 | `GET {prefix}/k/{id}`，服务端渲染，`no-store` + `noindex`，复用分享页的 CSP 与 `assets/share.js` | 保持「前缀只写一处」；不新增稳定文件名资源（否则要同步 `spa.stableAssetFiles`） |
| D9 | 收件人是 AI 怎么办 | 返回里同时给一段**可粘贴的提示词**（含 id + claim secret + 换取密钥的确切调用 + 指南地址） | AI 读不到 fragment（它不参与请求），所以必须有纯文本路径 |
| D10 | 重复领取 | 保持既有语义：领取即 `claimed`，再次领取 404（折叠为「不存在」）；页面用 `sessionStorage` 缓存已领到的密钥，**刷新同标签页仍可见** | 不改既有语义；缓存只解决「刷新一下密钥没了」这个真实且高频的踩脚 |
| D11 | id 是否泄漏 | **修订（2026-10-11，独立对抗验证后发现原表述与实现不符）**：接口层折叠（领取过的 id 与不存在的 id 返回**逐字节相同**的 404），但**页面层是存在性/状态 oracle**：持有 id 的人能看到 `open / claimed / expired / unknown` 四种状态、管理员填的 label、以及链接到期时间。**接受**这个差异 | 收件人必须读得懂「这条链接已经领过了」和「这是给你的」，否则一次误刷新就变成无从解释的失败；而 id 是 122 位 UUID、不可枚举，**能力在 fragment 而不是 id**。为免它退化成事故，加了 `TestKeyHandoffPageStateVisibility` 把「页面比接口多说」这件事钉成决定 |

| D12 | claim secret 的传输载体 | 用请求头 `X-Teleport-Claim`（浏览器与 agent 都自然），**并记录一条配置约束**：Caddy 默认只脱敏 `Authorization` / `Cookie`，**站点级 `log` 指令会把该头明文写盘**。当前生产无站点级 log（无访问日志），约束写进 `.ai/runbooks/caddy-routing-on-shared-host.md` | 头是唯一「既不进 URL、又能被非浏览器客户端使用」的载体；剩下的泄漏面只能在反向代理的日志配置上堵，所以把它变成一条写明的前置条件而不是隐形假设 |
| D13 | `HEAD` 请求 | 轮询端点对 `HEAD` 返回 **405 + `Allow: GET`** | Go 的 `ServeMux` 把 `HEAD` 交给 `GET` 模式；HEAD 没有响应体，于是一次带 claim 头的 HEAD 会**消耗掉一次性链接并把密钥扔掉**（代理/预取器/链接检查器会这么做）。独立对抗验证在生产上复现了这个后果 |

- **管理员**：面板填个名字 → 生成 → 复制「链接」或「提示词」发出去。**全程不需要第二次操作。**
- **收件人（人）**：打开链接 → 点领取 → 复制密钥（页面同时给现成的发布指引）。
- **收件人（AI）**：直接用提示词里的 `GET /api/agent-keys/applications/{id}` +
  `X-Teleport-Claim: <secret>` 换取密钥，再读 `/ai.md` 发布。
- **不变量未变**：服务端仍只存 `sha256(claim secret)`；明文密钥只在领取那一刻由 HMAC 派生出来。
- **可撤销**：领取前可在面板拒绝/失效那条 application；领取后按 key 撤销（既有能力）。
- **领取是不可逆的**：链接一旦被领取就无法恢复；因此凡是能让「非收件人」触发领取的路径都要堵死
  —— 已经堵了两条：链接预览（不执行 JS、拿不到 fragment，D7）与 `HEAD`（无响应体，D13）。

## 回滚

无 schema 变更。回滚二进制后：`/k/{id}` 页面消失（404），但已生成的 approved application
仍可被 agent 用原 claim secret 在既有轮询端点上领取 —— 也就是说回滚不会作废已发出的链接，
只是收件人得走 API 而不是页面。这是可接受的降级方向（功能变窄，权限不放大）。
